## The native linux-x64 host

A native `linux-x64` run was performed on 2026-08-28 and returns the three published digests
unchanged. It is recorded as a transcript, `measured/layer1-native-linux-x64.txt`:

```
# host linux-x64 node v22.22.2
p1	haps=20	sha256=90a5e26c296287cab14ebe64b2b41d4d503b040d8309c1bb6570ce86c4a0a7d6
p2	haps=28	sha256=4d4b0d1e8775f3617520c9c2f04f7360fac2a3b5d29df2c36e531be6835593da
p3	haps=32	sha256=f92aa8de573977d783beae803e9ce239051185aaaed1a2b515df746ea1ff09d0
```

and the comparison is a command with an exit code rather than a reader's eye:

```
$ pnpm verify:transcript results/measured/layer1-native-linux-x64.txt
# host linux-x64 node v22.22.2
p1  MATCH     haps=20  90a5e26c296287ca…
p2  MATCH     haps=28  4d4b0d1e8775f361…
p3  MATCH     haps=32  f92aa8de573977d7…
compared 3 patterns, 0 mismatched                    exit 0
```

**What this is, exactly.** This repository runs on `darwin-arm64`. It cannot execute a native
`linux-x64` run, so unlike the emulated row this one is **reported**, not re-derived here —
the same standing as the starred load figures in the layer-2 table and
`measured/artefact-reproduce-192.txt`. `verify:transcript` checks that a recorded run agrees
with the reference; it cannot check that the run happened or on what. Anyone with such a host
can close that gap in two commands — `node layer1/run.mjs > mine.txt` there, then
`pnpm verify:transcript mine.txt` — and layer 1 is exactly reproducible, so a disagreement is
a real finding rather than expected variance.

## CPU emulation is no longer an open question

The native row settles it. Whatever else differs between these three environments, **one of
them is not emulating a CPU**, and it produces the same three digests as the two that are or
were. So "the agreement is an artefact of running the amd64 image under emulation on the same
Apple-silicon machine" is not available as an explanation of the cross-environment result, and
no argument has to be accepted for that to be true.

The argument below is kept because it is still the honest account of the **emulated** arm, and
because it says something the native run does not: *why* emulation could not have been the
variable, which is a statement about layer 1's arithmetic rather than about which machines
happened to be available. It is no longer load-bearing.

## Why an emulated CPU was sound here and would not be for layer 2

Layer 1 executes **no floating point at all**. Hap times are exact `Fraction`s over `BigInt`
and are serialised as `n/d`, never through `valueOf()`. Since no FP executes, CPU emulation
cannot be the variable — while OS, libc, architecture target and Node build genuinely differ
and are exercised for real.

Layer 2 is about timing under contention, which is exactly what emulation confounds. That is
one of the two reasons there is no cross-host layer-2 table, and it is why the same host does
not license a layer-2 claim while an emulated host does not disqualify a layer-1 one.

Both rows stay. The emulated one is not redundant — it is the row with a different libc and a
different Node build, which the native row does not supply — and an argument kept only while it
was the only evidence is an argument nobody should have believed.

## The checks have been observed failing

A check that has only ever been green is not evidence.

### `pnpm cross-host`

Corrupting one digest in
`results/layer1-digests.txt` to `deadbeef…` and re-running:

```
p1  MISMATCH  linux=sha256=90a5e26c2962…  reference=sha256=deadbeef2962…
p2  MATCH     p3  MATCH
compared 3 patterns, 1 mismatched
exit 1
```

and clean again after restoring the reference (`exit 0`, `0 mismatched`, reference
byte-identical to the committed file). Note the exit code has to be read from the script
directly — behind a pipe, `$?` is the last command in the pipeline, not the script.

The script also refuses to report success when the container produced no digest lines to
compare (`VOID`, exit 2): a comparison with nothing on one side reports "no mismatches"
exactly like a clean one.

### `pnpm verify:transcript`

Same requirement, and it is stronger here: the transcript arm's green rests entirely on this
comparison, because the run behind it happened somewhere this repository cannot reach. So the
checker carries its own self-test, which builds each case rather than shipping fixtures that
could rot away from the parser they exercise:

```
$ pnpm verify:transcript --selftest
PASS  GREEN     a transcript equal to the reference               exit 0
PASS  RED       MUTATION — one digest corrupted to deadbeef…      exit 1
PASS  VOID-N    MUTATION — a transcript short by one pattern      exit 2
PASS  VOID-0    MUTATION — a transcript with no digest lines      exit 2

4 arms, 4 passed, 0 failed
```

And the self-test itself was red-proved, twice, from a committed base — because four arms that
have only ever passed say nothing about whether the self-test can report a failure:

| mutation to the checker | what the self-test did |
|---|---|
| `compare()` returns `{ code: 0 }` unconditionally | **FAIL RED** — `expected exit 1, got 0`; exit 1 |
| the pattern-count void guard disabled | **FAIL VOID-N** — `expected exit 2, got 1`; exit 1 |

Note which arm fires in each row. The always-green mutant leaves both VOID arms passing,
because the void guards run before the line it broke; the void-guard mutant leaves GREEN and
RED passing. Neither mutation is caught by the whole self-test — each is caught by one arm of
it, and a runner that printed only a total would have said `3 passed` both times.

Both mutations were reverted against a committed base and the revert checked by marker count
and by `cmp` against `git show HEAD:tools/verify-transcript.mjs`, not by reading a `git diff`:
a pathspec that matches nothing makes `git diff --quiet` exit 0 over a file that still holds
the mutant.
